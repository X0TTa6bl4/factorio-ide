# Событийный комбинатор для тестирования

## Назначение и статус

Событийный блок отсутствует в Factorio и моделирует окружение схемы. Пользователь пишет полноценный JavaScript на отдельной странице: наследник `EventCombinator` переопределяет `main`. По уточнению пользователя от **16.11.2026** он входит **в первый срез** вместе с минимальными Constant и Arithmetic. Он не заменяет четыре игровых типа и не экспортируется как игровой комбинатор.

Ниже — уточнённый проектный контракт для реализации задачи 0010, а не описание правил Factorio или отчёт о готовом коде. Согласованный принцип наследования и общих тиков сохранён; ранее незаданные формы действий и сообщения определены здесь.

## Конфигурация и состояние

```js
class ArrivalScenario extends EventCombinator {
    init() {
        this.state.arrived = false;
    }

    main() {
        if (this.nextTick === 10) {
            this.state.arrived = true;
            this.setOutput({
                red: true,
                green: false,
                signals: [{ signal: Signal.Signals.signal_A, constant: 1 }]
            });
        }
    }
}

const scenario = new ArrivalScenario({
    red_input: red_1,
    red_output: red_2,
    state: {},
    run: { every_tick: true, input_changed: false }
});
circuit.add(scenario);
```

- Четыре порта имеют общий тип «ссылка на сеть своего цвета или null»; пропущенный порт — null.
- `state` — начальное JSON-совместимое дерево, по умолчанию `{}`; копируется при каждом reset. Все изменяемые данные, необходимые следующему шагу, должны находиться в `this.state`.
- `run` при отсутствии равен `{every_tick:true,input_changed:false}`. При наличии оба поля обязательны и имеют тип boolean. Два false допустимы: остаются сообщения и назначенные пробуждения.
- `peers` — необязательный словарь имён в ссылки на событийные блоки текущего Circuit. В первом срезе словарь задаётся только `circuit.setPeers(event, {receiver})`: другое имя — ошибка конфигурации схемы. В runtime ссылка доступна как неизменяемый `this.peers.receiver`; при передаче Worker она кодируется стабильным ID. Разрешение завершается после регистрации всех устройств; неизвестная или чужая ссылка — ошибка сборки.
- Для взаимных ссылок сначала добавить оба блока, затем вызвать `circuit.setPeers(a, {receiver:b})` и `circuit.setPeers(b, {receiver:a})`. Это операция над описанием до старта; main не меняет топологию.
- Конструктор вызывает `super(config)`; он не должен запускать main, читать сети или создавать внешние эффекты. Регистрация — через общий [Circuit](api.md).
- Дополнительные постоянные поля/вспомогательные методы класса допустимы. Замыкания и частные изменяемые поля вне state не входят в гарантированный сохраняемый runtime; их нельзя использовать как скрытое состояние воспроизводимого сценария.

JSON-совместимое дерево: null, boolean, string, конечный Number, массивы и обычные объекты со строковыми ключами. Циклы, undefined, NaN/Infinity, BigInt, функции, Date/Map/Set и ссылки на устройства/сети в state или данных сообщений отклоняются на границе. При необходимости сценарий явно кодирует такие данные строками/обычными объектами.

## Начальная граница

`init()` — необязательный синхронный метод, вызывается один раз при создании прогона/reset. В нём можно менять state, устанавливать/очищать собственный выход, создавать импульс и назначать пробуждение. Чтение сетей и отправка сообщений в init запрещены, чтобы не зависеть от порядка инициализации.

Все блоки сначала инициализируются, затем общая граница 0 собирается из Constant и начальных событийных вкладов. Ошибка любого init отменяет подготовку всего прогона. Восстановление сохранённого runtime не вызывает init повторно.

## Чтение и время

| API | Значение |
|---|---|
| `this.tick` | Опубликованная граница t, только чтение |
| `this.nextTick` | Граница публикации t+1; в init равна 0 |
| `this.readSignal(signal, {red,green})` | int32-количество обычного канала с выбранных подключённых входов |
| `this.readSignals({red,green})` | Неизменяемый массив SignalCount присутствующих каналов, без нулевых итогов |
| `this.messages` | Неизменяемый массив сообщений, доставленных к границе t |

В чтении red/green — обязательные boolean. Оба false дают пустой набор, обычный отсутствующий сигнал — 0. Метасигнал не является аргументом readSignal; обход списка можно написать обычным JS. Снимки входов нельзя менять. Чтение чужих выходов или произвольных сетей через этот API не предоставляется.

Если результат должен появиться на тике 100, действие выполняется на шаге 99→100: проверять nextTick===100 либо назначить запуск на 99. Скорость интерфейса и системные часы не меняют номер тика.

## Свои выходы

```js
this.setOutput({ red: true, green: false, signals: [
    { signal: Signal.Signals.signal_A, constant: 5 }
] });
this.clearOutput({ red: false, green: true });
this.pulse({ red: true, green: true, signals: [
    { signal: Signal.Signals.signal_B, constant: 1 }
] }, 1);
```

`signals` — массив [SignalCount](api.md): строго обычный сигнал + constant int32. Дубли суммируются; метасигналы запрещены. Цветовые флаги обязательны. Оба false — допустимое отсутствие действия, но типы аргументов всё равно проверяются. Неподключённый выбранный порт не передаёт вклад в сеть.

| Действие | Точная семантика |
|---|---|
| setOutput | Полностью заменяет удерживаемую таблицу собственных сигналов выбранных цветов. Отсутствующие в новом списке каналы прежней удерживаемой таблицы исчезают. Другой цвет не меняется |
| setOutput с signals:[] | Очищает удерживаемую таблицу выбранных цветов, не отменяя их импульсы |
| clearOutput | Очищает удерживаемую таблицу и все активные импульсы выбранных цветов |
| pulse | Добавляет самостоятельный временный вклад выбранных цветов поверх удерживаемого; другие импульсы не отменяет |

Вызовы одного main применяются в порядке JS-вызовов: последний set заменяет удерживаемый выход; clear отменяет уже созданные импульсы этого цвета, а pulse после clear создаёт новый. Разные блоки не перезаписывают друг друга: их вклады суммируются в сети.

Длительность pulse — второй аргумент, положительный целый в тиках, по умолчанию 1. Если действие публикуется на границе b, импульс участвует в границах b...b+duration-1 и отсутствует начиная с b+duration. Для init b=0, для main b=nextTick. Завершение обрабатывает движок даже без вызова main. Импульсы складываются между собой и с удерживаемым вкладом по int32. Set не прерывает импульс; clear прерывает. Это проектный выбор, не имитация отдельного игрового устройства.

Пример: init устанавливает A=2; на 0→1 выдан pulse A=3 длительностью 2. На границах 0/1/2/3 количества равны 2/5/5/2, если других записей не было.

## Запуски и расписание

- Every tick запускает main на каждом шаге. Input changed сравнивает полную опубликованную таблицу подключённых входных сетей; два изменившихся входа дают один запуск.
- Первый шаг запускает main также в режиме input_changed, чтобы обработать начальный вход.
- `this.wakeAt(tick)` назначает запуск main при чтении границы tick (результат на tick+1). В main разрешён только будущий целый tick>this.tick; в init — tick>=0. Повторное назначение той же границы идемпотентно.
- `this.cancelWake(tick)` снимает это назначение. Прошлое назначение из main — ошибка, а не рекурсивный вызов.
- Доставленное сообщение будит получателя независимо от run.
- Совпадение нескольких причин не удваивает запуск: не более одного main блока на шаг. Наступившее назначение потребляется при успешной публикации.
- Окончание импульса пересчитывает собственный вклад без обязательного main. Эти дедлайны входят в runtime и учитываются оптимизированным планировщиком.

## Сообщения

```js
this.send(this.peers.receiver, {
    type: "train-arrived",
    data: { trainId: "train-1" }
});
```

Получатель — ссылка на EventCombinator той же схемы; строка имени сети не подходит. Полезная нагрузка строго `{type: nonempty string, data: JsonValue}`. Сообщение копируется при send, последующая мутация исходного data его не меняет.

Видимый получателю конверт: `{from, to, sentTick, deliveryTick, sequence, type, data}`, где from/to — стабильные ID, sentTick=t, deliveryTick=t+1. Sequence — счётчик отправок блока внутри текущего шага, начиная с 0. Порядок доставки: стабильный ID отправителя (обычное сравнение строк без locale), затем sequence. Перестановка массива устройств не меняет очередь.

Отправка на 0→1 становится доступна в messages при чтении границы 1; ответ получателя публикуется на 2. Сообщения доступны одному запуску main, затем удаляются при успешном commit. Ошибка шага не теряет входящие и не оставляет отправленные сообщения в опубликованной очереди. Прямой вызов чужого main и мутация чужого state запрещены контрактом. Замыкание сообщений не вызывает рекурсию в одном тике.

## RNG, асинхронность и ошибки

Сценарий может пользоваться `this.random()` — RNG модели с отдельным состоянием на блок, не RNG Factorio. Алгоритм первого среза — xorshift32: `x ^= x << 13; x ^= x >>> 17; x ^= x << 5; x >>>= 0`, результат `x / 4294967296`. Начальное состояние: uint32 от XOR project seed и FNV-1a-32 UTF-8 стабильного ID блока; нулевой результат заменить на `0x6d2b79f5`. FNV-1a: старт `2166136261`, для каждого байта XOR, затем `Math.imul(hash,16777619) >>> 0`. Seed Circuit по умолчанию 1. Из восстановленного состояния x=1 первые uint32-результаты — 270369, 67634689, 2647435461; сохраняются само x и порядок вызовов.

Использование Date, Math.random, внешних ответов и браузерных таймеров не входит в гарантию воспроизводимого сценария. Произвольный JS с такими источниками нельзя объявлять детерминированным только из-за наличия Worker.

В первом срезе init и main синхронны; возвращаемый Promise/thenable — ошибка. Свободный JS позволяет функции, циклы и собственные алгоритмы, но асинхронное ожидание не продвигает виртуальные тики. Сетевые API не входят в служебный контракт сценария. Worker сам по себе не обеспечивает сетевую изоляцию; внешние эффекты произвольного JS нельзя обещать откатить.

Шаг — общая транзакция: сети, свои выходы, state, RNG, сообщения, расписания и тик публикуются только после успешной подготовки всех устройств. Exception, неверный результат/state и timeout оставляют последнюю опубликованную границу, приостанавливают прогон и показывают блок, тик, тип ошибки и доступное место в коде. Для восстановления используются опубликованные сериализуемые состояния; нельзя продолжать вычисление из частично изменённого объекта.

## Worker и первый браузерный срез

Пользовательский код выполняется в останавливаемом Worker уже в первом срезе. Это не требует переноса всего движка: независимое ядро остаётся отдельным модулем. Для тестов ядра допустим управляемый исполнитель доверенных фикстур; отдельные браузерные тесты обязательно проверяют настоящий Worker.

Каждый запрос/ответ содержит runId, revision, stepId, phase и tick. Сначала prepare получает снимок и возвращает кандидат состояния/действий; ведущий движок валидирует его и делает общий commit. При abort Worker восстанавливается из последнего checkpoint; можно пересоздать Worker. Команды init/restore не смешиваются. Истечение лимита прерывает Worker; поздние ответы старого прогона не применяются.

Только один шаг находится в работе. Повторный запрос step до завершения отклоняется с диагностикой занятости. Reset отменяет незавершённый запрос, меняет runId и возвращает согласованную границу 0. Изменение кода приостанавливает прогон; успешная проверка создаёт новую revision и новый прогон.

Публичный исполнитель имеет асинхронные createSimulation/step/reset: `await circuit.createSimulation()`, `await simulation.step()`, `await simulation.reset()`. Один завершившийся step по-прежнему означает ровно один тик. Частота отрисовки не влияет на вычисление. Лимит длительности задания задаёт исполнитель, а не виртуальная схема; тесты проверяют timeout с управляемым пределом. Размещение Worker и модулей проверяется также под путём репозитория GitHub Pages.

Класс сценария — `EventCombinator`. Без своего `executor` схема с таким блоком получает встроенный синхронный исполнитель: он вызывает `init`/`main` и возвращает правку общей транзакции. `await createWorkerExecutor(worker, {scriptUrl, timeoutMs, profile})` подключает настоящий Worker. Модуль по `scriptUrl` экспортирует `devices` — массив классов в порядке добавленных событийных блоков; Worker создаёт из них экземпляры исполнения, а экземпляр на странице хранит порты, `state`, `run` и связь `receiver`. Команды `init` и `restore` не смешиваются.

`simulation.capture()` возвращает JSON-снимок опубликованной границы: сети, вклады, `state`, RNG, `seenInputs`, сообщения и пробуждения. `await simulation.restore(snapshot)` подставляет его без вызова `init` и без смены `runId`. Ограниченная история этих снимков, шаг назад и предел описаны в [тиках](factorio/ticks.md). Для встроенного и Worker-исполнителя `reset` заново вызывает `init` от начального `state`; снимок описания при этом не меняется. Чужой `executor` без `replayInit` по-прежнему восстанавливает границу 0 из checkpoint после первого `init`.

### Страница сценария и лимит хоста

Отдельная страница — `pages/event/index.html`. Стили и каркас берутся из библиотеки `ui/`; демонстрационные обработчики каталога к ней не подключаются. Пути к модулям и Worker относительные, поэтому страница открывается и из корня статического сервера, и под префиксом `/factorio-ide/` GitHub Pages. Прикладного HTTP API нет: сервер отвечает только на GET и HEAD.

Начальный текст страницы — сценарий Arrival. `init` ставит `state.arrived = false`. `main` при `nextTick === 1` пишет красный `signal-A = 1` и `arrived = true`. На границе 0 красная сеть пуста. Удержание сохраняет `signal-A = 1` на следующих границах, пока сценарий сам не изменит выход. Это проектная демонстрация Worker, не игровой эталон.

Редактор сценария пользуется тем же меню у каретки, что и конфигурация. Подсказки — свойства и методы поддержанного API: `this.tick`, `this.nextTick`, `this.state`, `this.messages`, `this.peers`, `this.readSignal`, `this.readSignals`, `this.setOutput`, `this.clearOutput`, `this.pulse`, `this.wakeAt`, `this.cancelWake`, `this.send`, `this.random`, а также `init`, `main` и `EventCombinator`. Это не языковой сервер JavaScript и не грамматика конфигурации комбинаторов: `Signal.*`, ключи устройств и сети оттуда не предлагаются. Комментарий и строка меню не открывают.

Редактор содержит один верхний `export class Имя extends EventCombinator`. Страница не вызывает этот код. Она собирает модуль: убирает `export` у этого класса, дописывает `export const devices` и импорт `EventCombinator` и `Signal` из `src/index.js` в конец файла. Комментарии, обычные строки и шаблонные литералы не считаются объявлением или импортом; код внутри `${...}` остаётся кодом. Заменяется только объявление в коде, поэтому номера строк тела класса совпадают с редактором. Модуль передаётся Worker как blob-URL в поле `scriptUrl`. Импорты в тексте сценария не принимаются: страница сама вводит `EventCombinator` и `Signal`.

Оболочка на странице — обычный `EventCombinator` с портами `red_1` и `green_1`. Вход и выход одного цвета соединены с одной сетью стенда. `state` и `run` берутся из формы. `main` оболочки не является пользовательским сценарием.

Лимит ожидания ответа Worker по умолчанию 1000 мс. Это целое число от 1 и настройка хоста: оно не меняет номер виртуального тика. Поле `revision` протокола остаётся номером контракта движка. Отдельный счётчик ревизии сценария на странице растёт только после успешной проверки.

Изменение кода или настроек запуска во время шага останавливает Worker. Текущий `prepare` отклоняется, частичный тик не публикуется, старая ревизия не применяется. Новый прогон начинается только после следующей успешной проверки. `executor.stop()` отклоняет все ждущие обмены кодом `worker-stopped` и завершает Worker. Истечение лимита отклоняет опоздавший обмен кодом `timeout` и тем же способом отпускает остальные ждущие обмены, чтобы управление не оставалось занятым. После timeout или остановки страница может создать новый Worker для того же проверенного модуля и продолжить с опубликованного checkpoint без `init`. `reset` увеличивает `runId` и снова вызывает `init`. `restore` вызывает `simulation.restore` и не меняет `runId`.

Диагностика показывает `code`, `deviceId`, `tick` и, если в стеке есть кадр вне `src/`, это место. Ошибка загрузки Worker останавливает попытку и снимает занятость.

Нарушение контракта сценария — `RuntimeError` или `ConfigError` с устойчивым `code` (`forbidden-read`, `forbidden-send`, `invalid-output`, `invalid-pulse`, `invalid-wake`, `unknown-wake`, `invalid-message`, `invalid-state`, `async-main`, `script-error`, `invalid-rng`, `invalid-snapshot`, `timeout`, `worker-stopped`). Исключение пользовательского кода получает `script-error`, `deviceId` и `tick`. Опубликованная граница при этом не меняется.

## Приёмка

- Arrival на nextTick=10 виден в сети на границе 10.
- Hold/pulse/clear дают определённые выше трассы в каждом цвете; вклад другого источника сохраняется.
- Сообщение шага 0→1 читается на 1 и влияет на выход получателя на 2.
- Совпавшие сеть, сообщение и wake дают один main; конец pulse работает без main.
- Reset, откат ошибки и восстановление повторяют сценарий для управляемого состояния и RNG.
- Зависший JS прерывается, интерфейс остаётся доступным; частичный тик и устаревший ответ не публикуются.
