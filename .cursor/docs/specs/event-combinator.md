# Событийный комбинатор для тестирования

## Согласованный контракт

Событийный комбинатор — дополнительная структура эмулятора, отсутствующая в Factorio. Основной редактор содержит конфигурацию схемы. На отдельной странице пользователь пишет полноценный JavaScript: наследуется от базового класса событийного комбинатора и переопределяет `main` под сценарий.

Класс получает ссылки на подключённые сети: красный и зелёный вход, красный и зелёный выход. Порты можно не задавать; их значения по умолчанию — `null`, как в [общем API](api.md). Блок читает сигналы, формирует собственный выходной вклад, имеет доступ к глобальному счётчику тиков симуляции и взаимодействует с другими событийными блоками.

Вызовы привязаны к тикам. Сценарий может зависеть от времени, изменений сетей или их сочетания. Изменение сети не должно вызывать рекурсивный внеочередной запуск внутри шага. Поведение, начальное содержимое и изменение выходов определяет пользовательский код; универсальный сигнал по умолчанию для всех сценариев не вводится.

Блок позволяет воспроизводить сигнальную логику станции, присутствие поезда, прибытие, отъезд и переходы между состояниями. Сейчас требуется описать этот механизм, а не реализовать общую транспортную модель. Координацию нескольких станций можно задавать взаимодействием сценариев.

Игровые типы остаются арифметическим, сравнивающим, постоянным и выбирающим. Событийный блок не экспортируется как игровой комбинатор и не заменяет эти типы. По решению пользователя он реализуется на втором этапе вместе с четырьмя игровыми типами и используется для их проверки; очередь описана в [плане развития](roadmap.md).

## Предлагаемая форма класса

Имя `EventCombinator` и служебные методы ниже — предложение API. Пользователь согласовал сам принцип наследования и переопределения `main`.

```js
class StationScenario extends EventCombinator {
    main() {
        // this.tick — опубликованный тик симуляции, только чтение.
        // Читать подключённые входы.
        // Менять собственное состояние и выходы.
        // Обмениваться событиями с другими сценариями.
    }
}

const station = new StationScenario({
    red_input: red_10,
    green_output: green_20
});
```

Базовый класс регистрирует подключения и режим пробуждений. При собственном конструкторе наследник передаёт конфигурацию в `super(config)`. Значение тика предоставляется движком, не вычисляется по системным часам и не записывается сценарием.

## Выполнение по тикам

1. На границе `t` доступны опубликованные входы, состояния и сообщения.
2. Движок выбирает блоки для запуска: по каждому тику, изменению подключённых входов или заранее назначенному тику. Согласованный режим по умолчанию — запуск `main` каждый тик; запуск по событиям задаётся явно. Нельзя автоматически решить, зависит ли произвольный JS от времени.
3. Выбранные блоки выполняют `main` не более одного раза за шаг. Чтение входов относится к `current[t]`; все выходные изменения накапливаются отдельно.
4. На границе `t+1` новые выходы и состояния публикуются одновременно с результатами остальных устройств.

Временная привязка должна быть явной: код, выполняемый на границе 99, формирует результат границы 100. Можно предоставить отдельное `nextTick`, чтобы сценарий «поезд прибыл на тике 100» не сдвигался из-за неоднозначного имени аргумента. Точное имя и API назначения события остаются открытыми.

Чтение выполняется через подключённые входы; запись заменяет или дополняет собственный вклад блока в его выходные сети. Изменять общую сетевую сумму непосредственно нельзя: это могло бы стереть выходы остальных источников. Политика объединения каналов и int32 общая с игровыми устройствами.

## Что означает «поведение выхода задаётся кодом»

Нужно предоставить выразимые действия для обоих сценариев:

- установить выход, который действует до следующего изменения;
- очистить собственный выход;
- выдать импульс на один или несколько тиков.

Удержание здесь означает конкретный пример: код установил A=1 один раз, а на следующем тике ничего с A не сделал. Останется ли вклад A=1 или исчезнет? Оба режима нужны для разных сценариев; пользователь определяет их своей программой, а базовый API должен явно различать действия.

Пользователь принял такой вариант действий как основу: `setOutput` устанавливает собственный выход до изменения/очистки; `clearOutput` очищает; `pulse` задаёт ограниченную длительность в тиках. Обязательное уточнение — выбор выходного цвета для каждого действия. Полная форма аргументов пока предложена, а не окончательно согласована:

```js
this.setOutput({ red: true, green: false, signals });
this.clearOutput({ red: false, green: true });
this.pulse({ red: true, green: true, signals }, 1);
```

Здесь `signals` — собственный набор выходных сигналов; формат списка описывается отдельно. `red`/`green` выбирают выходные порты, а не сети чтения. Можно выбрать красный, зелёный или оба цвета. Неподключённый порт ничего в сеть не передаёт. Действие для одного цвета не должно очищать собственный вклад в другой цвет. Выбор обоих цветов не сливает сети: вклад поступает в каждую из них.

У импульса необходимо определить начало, завершение, наложение на удерживаемый сигнал и несколько записей одного канала за шаг; не вводить скрытую очистку всех выходов только потому, что `main` не запускался.

Начальные сигналы также задаёт код. Механизм их задания ещё нужно описать: например, отдельная фаза инициализации или начальный выход конфигурации. При этом инициализация всех блоков должна завершаться до общего формирования границы `t=0`, без чтения частично подготовленных сетей.

## Взаимодействие событийных блоков

Согласован обмен через очередь: отправленное на шаге `t → t+1` сообщение становится доступно получателю на границе `t+1` и может повлиять на его следующий запуск. Так результат не зависит от позиции отправителя и получателя в массиве.

Ссылки на другие блоки можно передавать конфигурацией. Непосредственный вызов чужого `main` и изменение чужого состояния внутри своего шага не входят в предложенный протокол. Обычные вспомогательные методы собственного класса остаются свободным JS.

Для нескольких сообщений одной границы нужен воспроизводимый порядок, например стабильный ID отправителя и номер сообщения внутри отправителя. Допустимый формат сообщений и возможность чтения опубликованного состояния другого блока ещё требуется выбрать.

## Состояние, ошибки и воспроизводимость

Это предложения технического контракта, а не ограничения уже согласованного синтаксиса JavaScript:

- Данные, влияющие на последующие шаги, хранить в явно сохраняемом состоянии, например `this.state`, либо описывать методами сохранения/восстановления. Часы, RNG, очереди сообщений, расписание и собственные выходы входят в состояние прогона. Обычный снимок полей не восстанавливает произвольные замыкания.
- Для повторяемого сценария использовать тик симуляции, RNG с seed и расписание по тикам. Таймеры браузера, внешние ответы и системное время не должны определять воспроизводимый прогон. Доступность асинхронного JS и внешних API ещё не определена.
- При ошибке шаг не публикуется частично: симуляция приостанавливается, показываются блок, тик и место ошибки. Возможность восстановления полей пользовательского класса нужна также для такого отката.
- Пользовательский JS предлагается выполнять в отдельном останавливаемом Worker с ограничением длительности шага. Это сохраняет отзывчивость редактора при бесконечном цикле, но не обеспечивает полной изоляции: Worker сам по себе допускает сетевые запросы. Механизм ограничения доступных API пока не выбран. [Web Workers](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers).

## Оставшиеся решения

- Уточнить полные аргументы управления цветами выхода, импульсами и начальным состоянием.
- Уточнить API подписок/расписания и точное обозначение границы тика; сами режимы запуска `main` согласованы.
- Уточнить формат сообщений и правила доступа к чужому состоянию; доставка через следующую границу тика согласована.
- Выбрать способ сохранения пользовательского состояния и правила асинхронности/ошибок.

Согласованное наследование, четыре подключения, доступ к общему тику и взаимодействие блоков повторного подтверждения не требуют.
