# Общий план развития

Это предлагаемый порядок разработки по согласованным требованиям, без сроков и подробного дерева задач. На момент составления есть спецификации и каталог игровых данных; приложение ещё не реализовано. Планирование не запускает реализацию или публикацию.

Основные требования — в [проекте](project.md), формы объектов — в [API](api.md). Игровую семантику не дублировать здесь: перед реализацией сверять целевую stable по [совместимости](compatibility.md). Оставшиеся вопросы закрывать перед затронутым этапом; детализация событийного блока не должна задерживать проверку арифметики.

## 1. Основа движка и первая работающая схема

- Первой задачей подготовить рабочее окружение разработки и тестирования: устанавливаемые инструменты запускать через Docker, без установки Node.js и тестовых браузеров на хост. Это не меняет браузерный запуск для пользователя.
- Подготовить минимальную структуру HTML/CSS/JavaScript с нативными ES-модулями.
- Разделить описание схемы, состояние выполнения и интерфейс. Движок не зависит от DOM.
- Реализовать сети со стабильными ID, сигнальные токены, чтение/суммирование каналов и арифметику int32.
- Реализовать `step()` и `reset()`, буферы current/next, общую границу публикации.
- Регистрировать подключения и зависимости устройств. Первый расчёт выполнять полным проходом как эталон для последующего ускорения.
- Подключить постоянный и арифметический комбинаторы через классы с проверкой конфигурации. Использовать существующий каталог; для первых проверок достаточно небольшого набора каналов.
- Подготовить простую отладочную страницу с кнопкой шага и таблицей сигналов.

**Результат:** схема «постоянный → арифметический → сеть» работает по шагам. Проверены задержка, самоссылка, исчезновение вклада и независимость результата от порядка устройств.

## 2. Четыре игровых комбинатора и событийный

- Довести арифметический: операции, маски входов, Each, сбор результатов и числовые границы.
- Добавить сравнивающий: составные условия, метасигналы, фиксированное/копируемое количество, обе выходные ветки.
- Довести постоянный до явно определённого набора секций, групп и настроек.
- Добавить выбирающий по режимам, с учётом профиля данных, времени и воспроизводимой случайности.
- Реализовать событийный комбинатор: наследование, переопределение `main`, доступ к тику и подключённым входам, выходы с выбором цвета и импульсы.
- Поддержать запуск сценариев по тикам, изменениям входов и расписанию, обмен сообщениями через следующую границу тика.
- Добавить отдельную простую страницу JavaScript сценария, правила начального состояния, обработки ошибок и прерывания зависшего скрипта. Отдельный Worker для пользовательского кода не требует переноса всего движка.
- Подготовить событийные примеры: импульс на заданном тике, присутствие поезда на станции, отъезд по входному сигналу, взаимодействие двух сценариев.
- Перед реализацией каждого типа завершить относящуюся к нему форму конфигурации и спорные игровые случаи. Неподдержанные режимы диагностировать явно.

**Результат:** схемы из четырёх игровых типов дают ожидаемые последовательности тиков, а событийные блоки воспроизводят тестовое окружение. Есть поведенческие проверки движка и эталоны спорных случаев; соответствие игре заявляется только для действительно сверенных игровых возможностей.

## 3. Пошаговый отладчик в браузере

- Добавить запуск, паузу, управление скоростью просмотра и сброс поверх того же `step()`.
- Показывать тик, устройства, подключения, сигналы выбранных сетей и собственные выходы комбинаторов.
- Выделять изменившиеся значения и показывать ошибки настройки/расчёта.
- Подготовить несколько демонстрационных схем. Для начала достаточно списка устройств и таблиц; расположение блоков на холсте обсуждается отдельно.
- Подготовить возможность размещения статического приложения на GitHub Pages. Фактическая публикация выполняется отдельным поручением.

**Результат:** первая минимальная версия пригодна для проверки схем из четырёх игровых комбинаторов с событийным тестовым окружением в браузере. Остальные игровые устройства и история добавляются позднее.

## 4. Основной редактор и сохранение схем

- Добавить редактирование объектной конфигурации, подсказки констант Signal и операций, диагностику полей и сочетаний настроек.
- Реализовать автоматическое создание сетей, выдачу ссылок, подсказки существующих сетей и переименование с сохранением идентичности.
- Использовать общую модель схемы и те же проверки, что у движка. Основной редактор содержит конфигурацию; свободная логика относится к событийным сценариям.
- Добавить локальное сохранение, импорт/экспорт файла схемы и версию формата. Ссылки сохранять через стабильные ID, а не циклические объекты.
- Сохранять код событийных сценариев вместе со схемой; предусмотреть восстановление их состояния.
- Выбрать средства редактора и проверки JavaScript, не вводя заранее обязательный TypeScript или сборщик.

**Результат:** пользователь создаёт, исправляет, сохраняет и повторно открывает собственную схему. Её подключения и настройки сохраняют смысл после загрузки.

## 5. История и ускорение

- Добавить ограниченную историю снимков и шаг назад. Форму сохраняемого состояния учитывать с первого этапа, но сам откат не должен задерживать проверку ядра.
- Сохранять состояния устройств и сценариев, выходы, тик, RNG, очереди сообщений и будущие пробуждения.
- Реализовать пересчёт по зависимостям: регистрации подключений, очередь изменившихся читателей и сохранённые выходные вклады. Проверить эквивалентность первоначальному полному проходу.
- Измерить работу на больших схемах; перенос всего движка в Worker и дальнейшие оптимизации выполнять по результатам измерений.

**Результат:** откат и повтор шага воспроизводят результат; ускорение сохраняет прежнюю семантику тиков. Историю и оптимизацию можно выпускать независимо друг от друга.

## 6. Остальные устройства и дальнейшее развитие

- Добавлять необходимые устройства по реальным сценариям: станции, хранилища, лампы и другие согласованные блоки.
- Развивать упрощённую модель поездов: присутствие, прибытие, отправление, переход между станциями; полную физику движения не вводить автоматически.
- Отдельно определить необходимость визуального редактора проводов, импорта/экспорта blueprint и дополнительных средств анализа.

**Результат:** новые устройства используют уже проверенные сети и тики и могут сопоставляться с ранее написанными тестовыми сценариями.

## Ближайший приоритет

Первое поручение на реализацию стоит ограничить этапом 1: Docker-окружение разработки и тестов, постоянный и арифметический комбинаторы, корректный шаг и простая таблица сигналов. После его проверки расширять ядро до всех четырёх игровых типов и событийного комбинатора на этапе 2.
