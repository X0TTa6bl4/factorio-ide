# Выполнение по тикам

## Поведение Factorio

При обычной скорости игра выполняет 60 тиков за игровую секунду. Это не требование к частоте кадров браузера. [Time](https://wiki.factorio.com/Time).

Арифметический и сравнивающий комбинаторы имеют задержку в один тик. Логическая модель обновления: устройства читают входные сети и вычисляют выходы, затем сети получают сумму новых вкладов. Последовательная цепочка даёт задержку по вычислительным ступеням, а не по отдельным проводам. [Decider combinator](https://wiki.factorio.com/Decider_combinator), [описание обновления](https://wiki.factorio.com/Combinator_Tutorial).

Постоянный источник выдаёт настроенные значения без входа. API отдельно предоставляет выходы вычисляемых комбинаторов за прошлый тик; это полезное различие для отладчика. [Постоянный](https://wiki.factorio.com/Constant_combinator), [выходы прошлого тика](https://lua-api.factorio.com/latest/classes/LuaCombinatorControlBehavior.html).

## Проектная модель шага

Два буфера — способ реализации нашего симулятора. `current` — полностью опубликованное состояние границы тика `t`, `next` — строящееся состояние `t+1`. Ни один вычислитель не читает `next`.

Для начального этапа топология и настройки неизменны во время шага. Их редактирование приостанавливает расчёт и выполняет сброс; моделирование изменений «на лету» вводится отдельным контрактом.

1. Очистить `next` у всех сетей.
2. Прочитать входы каждого вычисляемого комбинатора только из `current`.
3. Вычислить его следующий выход и runtime-состояние. Результаты добавлять в `next` с учётом цвета выхода и int32.
4. Добавить вклады включённых постоянных источников. Не переносить старые сетевые суммы целиком.
5. Одновременно опубликовать все новые выходы, runtime-состояния и сети; обменять `current` и `next`, увеличить тик.
6. Обновить наблюдение и, если включена история, сохранить снимок.

Упрощённая запись:

```text
очистить(next)
для каждого вычисляемого устройства:
    результат, новое_состояние = вычислить(настройки, current, старое_состояние, t)
    добавить_выход(next, результат)
добавить_постоянные_источники(next)
опубликовать_всё_одновременно()
t = t + 1
```

Для `random` и `time` выбирающего общая граница публикации сохраняется, но правила обновления внутреннего выбора и чтения времени требуют отдельных тестов из [документа выбирающего](selector.md). Обычное правило «всё без состояния» к ним неприменимо.

## Пересчёт по изменениям сетей

Согласованное направление оптимизации: подключённые устройства регистрируются в сетях, чтобы движок вычислял зависящие от входов комбинаторы только при изменениях. Полный проход выше остаётся эталоном результата. Подписки сокращают вычисления, но не меняют задержку в один тик.

Предлагаемый алгоритм реализации:

1. При подготовке схемы построить список читателей каждой сети и очередь устройств на первый расчёт. Арифметический с двумя константами тоже должен вычислиться, хотя входные сети ему не нужны.
2. На шаге `t → t+1` пересчитать запланированные устройства по опубликованному `current[t]`. Одно устройство выполняется не более одного раза за шаг, даже если изменились обе сети.
3. Хранить собственный последний выход каждого устройства. Если пересчёт не нужен, его прежний вклад продолжает действовать; он не исчезает вместе с очисткой `next`.
4. Собрать `next` из новых и сохранённых вкладов, включая постоянные источники. Затем одновременно опубликовать результат.
5. Сравнить итог каждой изменявшейся сети с её прежним итогом по полным ключам и int32-значениям. Только реальные изменения опубликованного набора сигналов планируют читателей на следующий шаг `t+1 → t+2`. Изменение и исчезновение канала учитываются одинаково. Изменения вкладов, взаимно сократившиеся до прежней суммы сети, не требуют пересчёта читателей.

Не вызывать вычисление непосредственно из сетевого уведомления. Уведомление лишь добавляет устройство в очередь следующего шага. Самоссылка планирует новое вычисление через границу тика и не вызывает рекурсию.

Пример: постоянный вход A=1 и арифметический `A*10 → B`. После первого расчёта B=10. На следующем шаге вход не менялся, умножение можно пропустить, но вклад B=10 сохраняется. Если вход исчез, следующий расчёт заменяет старый вклад новым пустым выходом.

`time`, `random`, [событийный блок](../event-combinator.md) и другие устройства с внутренним временем должны будиться по расписанию/каждый тик, даже когда сети неизменны. Подписки только на входные сети для них недостаточны. Конкретные правила пробуждения относятся к контракту устройства.

Первый вариант может собирать сетевые суммы из всех сохранённых выходов: это экономит вычисления операций, но ещё требует прохода по источникам. Последующая оптимизация может обновлять только сети затронутых источников или применять разность старого и нового вкладов. Во всех вариантах старые сетевые суммы нельзя переносить вместе с повторным добавлением тех же вкладов.

Список подписчиков — служебный индекс движка; собственный выход устройства — вычислительный кэш, а не копия активирующих его входных сигналов. Настройки, переподключение и удаление обновляют зависимости; первоначальное правило редактирования со сбросом сохраняется.

## Начальная граница и обратные связи

Проектное правило сброса для четырёх игровых типов: `t=0`, вычисляемые выходы пусты, runtime-состояния и генераторы инициализированы, `current` собран из постоянных источников. Поэтому первый шаг уже читает константы. Это выбранная точка отсчёта симулятора, а не утверждение о порядке создания сущностей внутри игры. Начальное поведение событийных блоков задаётся их кодом; способ общей инициализации описывается отдельно в [контракте событийного блока](../event-combinator.md), без зависимых от порядка запусков.

Для самоссылки арифметического `A+1 → A`, без других источников:

| Опубликованный тик | A |
|---:|---:|
| 0 | 0 |
| 1 | 1 |
| 2 | 2 |
| 3 | 3 |

Рекурсивный обход и вычисление «до стабилизации» запрещены: они уничтожат смысл задержки. Цикл обрабатывается тем же проходом, что и линейная схема.

## История и воспроизводимость

Минимальный снимок содержит тик, опубликованные сигналы, runtime-состояния и состояние генератора случайности. При хранении отдельного кэша выходов он тоже входит в снимок. Очередь пересчёта и запланированные пробуждения необходимо сохранить либо однозначно восстановить без повторного исполнения сценариев. `next` — рабочий буфер, его можно очистить при восстановлении.

Шаг назад восстанавливает снимок, а не обращает арифметические операции. История ограничена; её предел остаётся параметром проекта. Отрисовка и реальное время не влияют на результат `step()`.

## Проверки движка

- Перестановка массива устройств не меняет опубликованный результат.
- Сигнал проходит два вычисляемых устройства за два шага.
- Самоссылка даёт последовательность таблицы; цикл не вызывает рекурсию.
- Пропавший вклад исчезает после соответствующей публикации, без накопления в `next`.
- Сброс повторяет начальную границу; восстановление снимка и повтор шага дают тот же результат, включая случайный режим симулятора.
- Пересчёт по зависимостям даёт те же границы, что полный проход: неизменные выходы сохраняются, исчезнувшие удаляются, циклы и два одновременно изменившихся входа не дают лишних вычислений внутри тика.
