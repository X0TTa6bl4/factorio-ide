# Выполнение по тикам

## Поведение Factorio

При обычной скорости игра выполняет 60 тиков за игровую секунду. Это не требование к частоте кадров браузера. [Time](https://wiki.factorio.com/Time).

Арифметический и сравнивающий комбинаторы имеют задержку в один тик. Логическая модель обновления: устройства читают входные сети и вычисляют выходы, затем сети получают сумму новых вкладов. Последовательная цепочка даёт задержку по вычислительным ступеням, а не по отдельным проводам. [Decider combinator](https://wiki.factorio.com/Decider_combinator), [описание обновления](https://wiki.factorio.com/Combinator_Tutorial).

Постоянный источник выдаёт настроенные значения без входа. API отдельно предоставляет выходы вычисляемых комбинаторов за прошлый тик; это полезное различие для отладчика. [Постоянный](https://wiki.factorio.com/Constant_combinator), [выходы прошлого тика](https://lua-api.factorio.com/latest/classes/LuaCombinatorControlBehavior.html).

## Проектная модель шага

Два буфера — способ реализации нашего симулятора. `current` — полностью опубликованное состояние границы тика `t`, `next` — строящееся состояние `t+1`. Ни один вычислитель не читает `next`.

Для начального этапа топология и настройки неизменны во время шага. Их редактирование приостанавливает расчёт и выполняет сброс; моделирование изменений «на лету» вводится отдельным контрактом. Вклад постоянного, включая секции и фильтры группы, фиксируется при создании прогона. Следующие границы и `reset` повторяют этот снимок. Новый прогон читает группу заново и публикует её на своей границе 0.

1. Очистить `next` у всех сетей.
2. Прочитать входы каждого вычисляемого комбинатора только из `current`.
3. Вычислить его следующий выход и runtime-состояние. Результаты добавлять в `next` с учётом цвета выхода и int32.
4. Добавить вклады включённых постоянных источников. Не переносить старые сетевые суммы целиком.
5. Собрать сети из выходов комбинаторов и постоянных источников. Граница ещё не видна читателю.
6. Для лампы прочитать эти сети и записать `{ lit, color }`. Лампа не добавляет вклад. Затем одновременно опубликовать сети, выходы и состояние; если включена история, сохранить снимок.

Упрощённая запись:

```text
очистить(next)
для каждого вычисляемого устройства:
    результат, новое_состояние = вычислить(настройки, current, старое_состояние, t)
    добавить_выход(next, результат)
добавить_постоянные_источники(next)
опубликовать_сети()
для каждой лампы:
    состояние = наблюдать(опубликованные сети этой границы)
опубликовать_состояние()
t = t + 1
```

Лампа — наблюдатель, не комбинатор. Она видит суммы постоянных источников и выходы комбинаторов той же границы и ничего не пишет обратно. Поэтому прямое подключение к постоянному источнику видно уже на границе 0, а выход арифметического — на границе его публикации, без второй задержки. Это проектное правило шага: запуск Factorio для такта лампы не выполнялся. Оптимизированный проход повторяет наблюдение, только если входная сеть лампы изменилась; иначе сохраняется прежнее состояние.

Для `random` и `time` выбирающего общая граница публикации сохраняется. `random` на каждом шаге обновляет снимок `{ rng, held, elapsed }`; `time` читает `origin + s` на границе `s` и публикует результат на `s + 1`. Подробности и спорные ветви — в [документе выбирающего](selector.md). Обычное правило «всё без состояния» к ним неприменимо.

## Асинхронный исполнитель и событийные вклады

В первом срезе пользовательский сценарий уже работает в Worker. Публичный step возвращает Promise; после успешного await опубликован ровно один следующий тик. Входы заморожены на t, кандидат событийного состояния возвращается в prepare и публикуется вместе с игровыми устройствами. Второй одновременный step отклоняется. При ошибке/timeout тик, очереди и все состояния остаются на прошлой границе; reset отменяет текущий запрос и меняет runId. Чистое ядро не зависит от Worker/DOM.

Удерживаемые выходы, слои импульсов, их сроки, RNG и сообщения участвуют в общей транзакции. Окончание pulse действует даже без main. Начальные событийные выходы добавляются при t=0 только после успешного init всех блоков. Детали — в [событийном контракте](../event-combinator.md).

## Пересчёт по изменениям сетей

Согласованное направление оптимизации: подключённые устройства регистрируются в сетях, чтобы движок вычислял зависящие от входов комбинаторы только при изменениях. Полный проход выше остаётся эталоном результата. Подписки сокращают вычисления, но не меняют задержку в один тик.

Предлагаемый алгоритм реализации:

1. При подготовке схемы построить список читателей каждой сети и очередь устройств на первый расчёт. Арифметический с двумя константами тоже должен вычислиться, хотя входные сети ему не нужны.
2. На шаге `t → t+1` пересчитать запланированные устройства по опубликованному `current[t]`. Одно устройство выполняется не более одного раза за шаг, даже если изменились обе сети.
3. Хранить собственный последний выход каждого устройства. Если пересчёт не нужен, его прежний вклад продолжает действовать; он не исчезает вместе с очисткой `next`.
4. Собрать `next` из новых и сохранённых вкладов, включая постоянные источники. Затем одновременно опубликовать результат.
5. Сравнить итог каждой изменявшейся сети с её прежним итогом по полным ключам и int32-значениям. Только реальные изменения опубликованного набора сигналов планируют читателей на следующий шаг `t+1 → t+2`. Изменение и исчезновение канала учитываются одинаково. Изменения вкладов, взаимно сократившиеся до прежней суммы сети, не требуют пересчёта читателей.

Не вызывать вычисление непосредственно из сетевого уведомления. Уведомление лишь добавляет устройство в очередь следующего шага. Самоссылка планирует новое вычисление через границу тика и не вызывает рекурсию.

Пример: постоянный вход A=1 и арифметический `A*10 → B`. После первого расчёта B=10. На следующем шаге вход не менялся, умножение можно пропустить, но вклад B=10 сохраняется. Если вход исчез, следующий расчёт заменяет старый вклад новым пустым выходом.

`time`, `random`, [событийный блок](../event-combinator.md) и другие устройства с внутренним временем должны будиться по расписанию/каждый тик, даже когда сети неизменны. Подписки только на входные сети для них недостаточны. Конкретные правила пробуждения относятся к контракту устройства.

Первый вариант может собирать сетевые суммы из всех сохранённых выходов: это экономит вычисления операций, но ещё требует прохода по источникам. Последующая оптимизация может обновлять только сети затронутых источников или применять разность старого и нового вкладов. Во всех вариантах старые сетевые суммы нельзя переносить вместе с повторным добавлением тех же вкладов.

Список подписчиков — служебный индекс движка; собственный выход устройства — вычислительный кэш, а не копия активирующих его входных сигналов. Настройки, переподключение и удаление обновляют зависимости; первоначальное правило редактирования со сбросом сохраняется.

## Начальная граница и обратные связи

Проектное правило сброса для четырёх игровых типов: `t=0`, вычисляемые выходы пусты, runtime-состояния и генераторы инициализированы, `current` собран из постоянных источников. Поэтому первый шаг уже читает константы. Это выбранная точка отсчёта симулятора, а не утверждение о порядке создания сущностей внутри игры. Начальное поведение событийных блоков задаётся их кодом; фаза init и общая атомарная инициализация определены в [контракте событийного блока](../event-combinator.md), без зависимых от порядка запусков.

Для самоссылки арифметического `A+1 → A`, без других источников:

| Опубликованный тик | A |
|---:|---:|
| 0 | 0 |
| 1 | 1 |
| 2 | 2 |
| 3 | 3 |

Постоянный `A=1` и арифметический `A+1 → A` в той же сети не заменяют вклад друг друга. На границе 0 видна только константа. Каждый следующий выход арифметического прибавляется к ней через int32:

| Опубликованный тик | A |
|---:|---:|
| 0 | 1 |
| 1 | 3 |
| 2 | 5 |
| 3 | 7 |

Обе таблицы — проектная модель задержки, не игровой fixture. Рекурсивный обход и вычисление «до стабилизации» запрещены: они уничтожат смысл задержки. Цикл обрабатывается тем же проходом, что и линейная схема. Цепочка из нескольких вычисляемых устройств, включая выбирающий и событийный блок, прибавляет по одной границе на устройство. Ошибка любого участника шага не публикует эту границу: уже видимые вклады соседей остаются.

## История и воспроизводимость

Снимок — JSON опубликованной границы, который возвращает `simulation.capture()` и принимает `simulation.restore(snapshot)`. Это проектный контракт симулятора, не сохранение Factorio и не файл схемы. Файл версии 1 по-прежнему не содержит runtime.

В снимок входят тик, профиль, версия игры, сигналы каждой сети прогона и по каждому устройству: `output`, `held`, `pulses`, `state`, `rng`, `seenInputs`, `messages`, `wakes`. `output` и `held` — кэш вкладов, не сумма сети. `state` сценария и `data` сообщения — JSON-дерево: `null`, boolean, конечное число, строка, массив и простой объект, без циклов, функций и посторонних типов. RNG событийного блока — целое uint32; у выбирающего `random` состояние `{ rng, held, elapsed }` тоже uint32. Это xorshift32 модели, не генератор Factorio. `messages` — очередь доставки с конвертом `from`, `to`, `sentTick`, `deliveryTick`, `sequence`, `type`, `data`. `wakes` — будущие границы пробуждения.

Состояние станции в снимке — `{ present, trainId }`, состояние поезда — фаза, индексы, `remaining`, маршрут и station ID. Очереди ожидания у этой модели нет. Переход считается в той же публикации, что и остальные устройства: вход отправления берётся с текущей границы, новое присутствие выходит на следующей. Конфликт станции не публикует границу. Правила — в [поездах](trains.md).

`next` в снимок не входит и при восстановлении пуст. Отдельной очереди пересчёта в полном проходе нет: следующий шаг однозначно читает восстановленную границу. Вычисляемые устройства считаются снова, участники сценария просыпаются по восстановленным `wakes`, `messages` и `seenInputs`. `restore`, `back` и `recall` не вызывают `init`, `main` и `compute`. Когда появится очередь читателей, её нужно будет хранить в снимке либо так же однозначно строить из границы; до этого задачи она не влияет на результат.

История хранит глубокие копии снимков успешных границ. Предел — целое число от 1, параметр `historyLimit` у `createSimulation`. Если параметр опущен, предел равен 32. Ноль, дробь и нечисло дают `invalid-simulation-options`, прогон не создаётся. После границы 0 каждый успешный `step` дописывает снимок. Сверх предела вытесняется самая старая граница; текущая остаётся. Неуспешный шаг историю не дополняет.

`historyTicks()` перечисляет сохранённые тики от старого к новому. `historySnapshot(tick)` возвращает копию снимка или `null`. `back()` восстанавливает предыдущую сохранённую границу и отбрасывает более новую. `recall(tick)` делает то же для выбранного сохранённого тика. Текущий тик при `recall` не переписывается. После отката следующий `step` создаёт новую ветку и не подставляет отброшенное будущее. Чужой `restore` известного тика так же отрезает будущее и заменяет границу этого тика; `restore` тика, которого в истории нет, оставляет историю из одной этой границы.

`reset` публикует границу 0 по прежнему правилу исполнителя и оставляет в истории только её. Откат не отменяет `reset` и не проигрывает отброшенные шаги. Изменение уже возвращённого объекта `capture()` или `historySnapshot()` не меняет ни прогон, ни сохранённую копию.

Ошибки атомарны: опубликованная граница и список истории остаются прежними. Код `invalid-snapshot` — чужая или неполная форма. Код `invalid-state` — несериализуемое `state` или `data`. Код `history-exhausted` — `back()` при одной сохранённой границе. Код `history-missing` — тика нет среди сохранённых. Код `step-busy` — откат или `restore` во время шага. Отрисовка и реальное время не влияют на `step()`.

Шаг назад восстанавливает снимок, а не обращает арифметические операции.

## Проверки движка

- Перестановка массива устройств не меняет опубликованный результат.
- Сигнал проходит два вычисляемых устройства за два шага.
- Самоссылка даёт последовательность таблицы; вместе с постоянным `A=1` сумма идёт 1, 3, 5, 7. Цикл не вызывает рекурсию.
- Пропавший вклад исчезает после соответствующей публикации, без накопления в `next`.
- Сброс повторяет начальную границу; восстановление снимка и повтор шага дают тот же результат, включая случайный режим симулятора.
- Пересчёт по зависимостям даёт те же границы, что полный проход: неизменные выходы сохраняются, исчезнувшие удаляются, циклы и два одновременно изменившихся входа не дают лишних вычислений внутри тика.
