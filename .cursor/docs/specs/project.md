# Требования к проекту

## Назначение

`f logic` — лёгкий браузерный инструмент для проектирования и пошаговой проверки логических сетей Factorio вне игры. Референс — [cnide](https://github.com/charredUtensil/cnide). Конфигурация задаётся через JavaScript API классов комбинаторов; редактор и движок используют общую модель схемы, сигналы доступны для просмотра по тикам. Первоначальное предложение собственного C-подобного псевдоязыка заменено объектной конфигурацией.

## Запуск и публикация

- Исходный код публикуется на GitHub; приложение — через GitHub Pages.
- Пользователь открывает публичную ссылку в современном браузере. Скачивать репозиторий, устанавливать Node.js или запускать команды не требуется.
- Симуляция, редактирование и просмотр результата выполняются на устройстве пользователя. Для первого этапа прикладной сервер и аккаунт не нужны.
- Открытие локального `index.html` двойным кликом и полный офлайн-режим не являются обязательными требованиями.
- Данные схем предполагается хранить в браузере и переносить через импорт/экспорт файла; это отдельная функция, не облачное сохранение.

GitHub Pages обслуживает статические HTML/CSS/JS-файлы. Публикацию можно автоматизировать после изменения исходников; обязательного этапа сборки нет. [GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages).

## Согласованный стек

Решение согласовано 10 ноября 2026 года.

| Часть | Технология и назначение |
|---|---|
| Структура интерфейса | HTML |
| Оформление | CSS |
| Движок и поведение интерфейса | Обычный JavaScript |
| Организация кода | Нативные ES-модули с `import` и `export` |
| Выполнение | Браузер пользователя |
| Размещение | Статические файлы на GitHub Pages |

Начальный вариант разрабатывается без обязательного сборщика и сторонних библиотек. TypeScript, Vite и UI-фреймворк в согласованный стек не входят. Инструменты типизации JavaScript, разбора конфигурации и редактора выбираются отдельно по мере детализации этих функций.

### Окружение разработки и тестирования

Если для разработки или тестирования нужно установить инструменты, они устанавливаются и запускаются через Docker. Подготовка этого окружения — первая задача реализации. Node.js, средства покрытия и тестовые браузеры не должны требовать отдельной установки на хост; версии контейнеров и пакетов фиксируются при создании контура. При отсутствии Docker описать его установку для платформы разработчика; не устанавливать его автоматически в ходе планирования.

Тестовые зависимости допустимы внутри контура разработки и не становятся обязательными библиотеками приложения. Для движка и комбинаторов требуется максимальное покрытие поведения и достижимых ветвей по [стратегии тестирования](../../tasks/0001-epic-_-f-logic-implementation/media/testing-strategy.md). Конкретные команды появятся после создания окружения; сейчас тестовый контур не реализован.

### Движок

- Движок — самостоятельные JavaScript-модули без зависимости от DOM, элементов интерфейса и таймера отрисовки.
- Описание схемы отделено от состояния выполнения. Объектный API и UI используют общую модель схемы.
- Один вызов `step()` выполняет ровно один тик; `reset()` восстанавливает начальное состояние. Интерфейс получает опубликованное состояние для отображения.
- Ручной шаг и автоматический запуск используют один алгоритм. Частота вызовов и отрисовки определяет скорость просмотра, но не результат последовательности тиков.
- Арифметика сигналов реализуется отдельными функциями с правилами int32 из [спецификации сетей](factorio/networks.md); обычное поведение `Number` не считается достаточным для совместимости.

### Web Worker

На начальном этапе движок может выполняться в основном потоке страницы. Web Worker — предусмотренная возможность дальнейшего развития, если длительные вычисления начнут мешать отзывчивости интерфейса; его реализация не является условием первого этапа.

При переносе в Worker интерфейс отправляет команды сообщениями и получает результаты для отображения. Worker не обращается к DOM. Алгоритм тика и модель схемы сохраняются; обмен сообщениями организуется вокруг независимого движка. Откат добавляется согласно требованиям к истории, отдельно от выбора потока выполнения.

## Последовательность разработки

Предлагаемый порядок, зависимости и результаты этапов собраны в [плане развития](roadmap.md). Приоритет — корректные сети и тики, затем на втором этапе четыре игровых комбинатора вместе с событийным тестовым блоком. Далее развиваются браузерный отладчик, основной редактор и сохранение; остальные игровые устройства добавляются на проверенное ядро.

История с шагом назад желательна, но не должна задерживать проверку ядра. Визуальный редактор проводов и экспорт blueprint требуют отдельной детализации.

## Границы модели

Сети хранятся в массиве и имеют стабильные ID. Вычисляемые комбинаторы ссылаются на красную и зелёную сети входа и выхода. Постоянный источник имеет только выходную сторону. Описание схемы, runtime-состояние и UI разделяются; движок работает без DOM.

Упрощение первого этапа: вычисляемые комбинаторы считаются полностью обеспеченными электричеством; строительство, исследования и энергосистема не симулируются. Неподдержанный режим должен выдавать диагностику, а не незаметно заменяться пустым выходом.

Подробности — [сети](factorio/networks.md), [тики](factorio/ticks.md). Версия игры — [последняя стабильная](compatibility.md).

## Контракты и открытые вопросы

Формы конфигурации, типы операндов, константы и выходные ветки определены в [объектном API](api.md). Подсказки, диагностика и повторная проверка перед запуском — в [правилах редактора](editor.md).

Сети автоматически создаёт редактор/движок; неподключённые порты можно пропускать. `null` означает незаданный операнд, а условие сравнивающего с таким операндом ложно. Подробные договорённости и оставшиеся вопросы собраны в [API](api.md). Основной редактор содержит конфигурацию; свободный JS тестового окружения задаётся наследником [событийного комбинатора](event-combinator.md) с переопределённым `main`, доступом к тику, сетям и другим сценариям. Его реализация включена во второй этап; детали служебного API ещё обсуждаются. Не подменять открытые решения самостоятельно выбранными значениями по умолчанию. Непроверенные игровые случаи хранятся в документах конкретных устройств.

## Критерии приёмки первого этапа

- Схему из четырёх поддержанных типов можно настроить и выполнить по одному тику в браузере.
- Видны номер тика, сигналы выбранной сети и выходы выбранного устройства.
- Порядок устройств в массиве не меняет результат; обратные связи не требуют рекурсии.
- Поддержанные режимы имеют поведенческие проверки; неподдержанные явно обозначены.
- Приложение открывается по ссылке GitHub Pages без локальной установки и работает без прикладного сервера.
- Опубликованная версия показывает, с какой стабильной версией Factorio проверена совместимость.
