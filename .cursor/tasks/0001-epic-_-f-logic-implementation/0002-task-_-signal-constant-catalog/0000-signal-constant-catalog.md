Дополнительная проверка этих сведений выполняется по мере необходимости соответствующих функций. Исторические записи о blocked и предыдущих числах ниже не являются текущим статусом.

## Требования к именам

1. Источник — `prototype.name`, а не label/перевод и не тип прототипа. `wooden-chest → wooden_chest`, `signal-A → signal_A`: дефис заменяется подчёркиванием, регистр сохраняется.
2. Форма — `Signal.<раздел>.<имя>`, например `Signal.Logistic.wooden_chest`. Разделы остаются десятью согласованными классами; Recipe/Entity-ветви не добавлять.
3. Метасигналы используют реальные имена: `Signal.Meta.signal_each`, `signal_everything`, `signal_anything`. Их токены не становятся обычными сетевыми каналами.
4. Исходный name сохраняется неизменным рядом с publicName; нормализованная строка не является игровым ключом.
5. Сначала проверить реальные данные выбранных профилей: есть ли два доступных сигнала с одним publicPath или имена, которые после согласованной замены дефиса нельзя использовать в JavaScript-доступе через точку. `a-b/a_b` и одинаковый name разных типов — примеры для проверки, а не утверждение о наличии конфликта. Не вводить заранее переименования, смену регистра и числовые/типовые суффиксы вроде `_item` или `_recipe`. Если конфликт обнаружен, включить конкретные игровые ID и предполагаемый publicPath в отчёт и только затем предложить точечное решение. Если конфликтов нет, сохранить действующее правило, включая `Signal.Logistic.wooden_chest`, без дополнительных преобразований.
6. Если источники доказывают, что запись не выбирается как обычный сигнал, сохранить её с ролью/причиной исключения. Совпадающая иконка сама по себе не означает одинаковую идентичность.


### Эталон публичного набора: постоянный комбинатор

По уточнению пользователя 18.11.2026 источником общего публичного набора обычных сигналов служит фактическое меню выбора сигнала постоянного комбинатора. Сформировать отдельные проверенные наборы для base и полного Space Age целевой stable, с игровыми type/name, подписями, разделами/подгруппами, порядком и источником проверки. Сырое множество прототипов хранить для учёта, не экспортировать его целиком как пользовательский список.

Сохранять версию, активные официальные пакеты, режим игры и настройки видимости/параметров, влияющие на меню. Подтверждать именно выбор из меню, а не только возможность вставить сигнал консолью, модом или импортом blueprint. Черновик/blueprint с «каждым сигналом» — кандидат для сравнения: принятие его игрой не доказывает ни доступности всех записей через chooser, ни полноты набора. Для проверки допустимости чтения/записи секций использовать API целевой версии; результаты ручного выбора можно выгрузить из секций постоянного комбинатора или экспортированного blueprint, сохранив происхождение и охват вкладок. Выгрузка только выбранных слотов без проверки охвата не является полным меню.

Тот же набор обычных сигналов использовать для входных/выходных сигналов других комбинаторов, не создавать независимые справочники с разными именами. Проверки конкретного поля/операции остаются отдельными: общий набор не означает, что любой тип подходит для любого режима устройства. Each/Everything/Anything, wildcard качества и параметры чертежей учитывать отдельно по допустимым контекстам; отсутствие метасигнала в постоянном комбинаторе не исключает его из сравнивающего/арифметического.

Для астероидов и биолаборатории сначала сверить записи с этим эталоном. Не изобретать дополнительный публичный сигнал для прототипа, которого нет в меню. Если отдельный runtime допустим, но скрыт из выбора, это техническая запись с явным статусом, а не обязательный пользовательский экспорт. Ранее переименованные развалины также проверить на соответствие выбранному публичному набору; правильный синтаксис JS сам по себе не доказывает наличие в chooser.

### Уточнение 18.11.2026: бочки и захваченный улей

Это требования к следующей доработке реализации. В рамках текущего поручения изменяется только задача; код, каталоги и спецификации не правятся, генерация и тесты не запускаются.

Для бочки с каждой жидкостью использовать предмет как основной токен, а рецепты — как вложенные константы:

| Публичный путь | Игровой ID | Назначение |
|---|---|---|
| `Signal.Intermediate.barrel` | `item/barrel` | Пустая бочка |
| `Signal.Intermediate.water_barrel` | `item/water-barrel` | Вода (бочка) |
| `Signal.Intermediate.water_barrel.fill` | `recipe/water-barrel` | Наполнить бочку (Вода) |
| `Signal.Intermediate.water_barrel.empty` | `recipe/empty-water-barrel` | Опустошить бочку (Вода) |

`fill` и `empty` взяты из игровых названий действий **Fill** и **Empty**. Ключи локализации — `recipe-name.fill-barrel` и `recipe-name.empty-filled-barrel`, подгруппы — `fill-barrel` и `empty-barrel`. Внутреннее имя рецепта наполнения не содержит префикса fill: для воды это `water-barrel`; для опустошения — `empty-water-barrel`. Вложенные пути — соглашение нашего API, а не готовые имена из Factorio.

Это общее правило для всех семи жидкостей base и девяти полного Space Age: холодный и горячий фторкетон обрабатываются точно так же. Пустая бочка — отдельный предмет `barrel`, не действие `.empty`. Рецепт изготовления самой пустой бочки не является опустошением. Скрытые recycling-рецепты не становятся действиями наполнения/опустошения.

Для рецептов действий `publicName` — лист `fill` или `empty`, `publicPath` — полный вложенный путь; исходные `gameName` и `prototypeId` сохраняются. Предмет остаётся полноценным неизменяемым токеном; `.fill` и `.empty` возвращают отдельные неизменяемые токены типа `recipe`, не выполняют крафт и не меняют предметный токен. При реализации расширить индекс и round-trip на пути переменной глубины; не ограничивать доступ тремя сегментами. Не создавать несогласованные плоские дубли для тех же рецептов.

По указанию пользователя для захваченного улья экспортировать только `Signal.Production.captive_biter_spawner` → `item/captive-biter-spawner`. Запись `entity/captive-biter-spawner` сохранить в полном учёте с причиной отсутствия публичного пути: принятое решение проекта «только предмет». Не добавлять её в `Signal.Enemies`. Сообщение пользователя об отсутствии в разделе врагов не выдавать за подтверждённый runtime-флаг скрытия или универсальное правило для всех сущностей.

### Астероиды: наблюдения пользователя и техническое сопоставление

Пример пересечения исходных записей: `item/metallic-asteroid-chunk` и `asteroid-chunk/metallic-asteroid-chunk`. У обеих подпись «Кусок металлического астероида», группа `space`, подгруппа `space-material`; построение пути только из группы и имени даёт обеим `Signal.Space.metallic_asteroid_chunk`. Так же устроены carbonic, oxide и promethium.

По сообщению пользователя 18.11.2026 в меню есть ровно по одному варианту каждого куска: металлического, углеродного, оксидного и прометиевого. Вопрос о числе вариантов закрыт ручным наблюдением пользователя. Версия, пакеты и настройки этого наблюдения не указаны. Для каждого куска предусмотреть один публичный путь по действующему правилу имени: `Signal.Space.metallic_asteroid_chunk`, `Signal.Space.carbonic_asteroid_chunk`, `Signal.Space.oxide_asteroid_chunk`, `Signal.Space.promethium_asteroid_chunk`. Вторые пути для летящих фрагментов не изобретать и повторно не просить пользователя выбирать между двумя вариантами меню.

Техническое сопоставление единственного выбранного сигнала с игровым `type/name` остаётся работой исполнителя задачи. Само число вариантов не доказывает, что сохранённый тип — item, и не устанавливает runtime-значения `hide_from_signal_gui`/`item_signal_alias`. Получить ключ выбранного сигнала и, при доступности нужной среды, эти runtime-поля; сохранить обе исходные записи с явным статусом экспорта/связи. Не сливать игровые ID и не выводить значение отсутствующего поля из `hidden: false`.

Различие исходных типов: `asteroid-chunk/<name>` описывает летящий фрагмент в космосе, а `item/<name>` — соответствующий предмет после сбора, используемый в инвентаре и рецептах. Это объясняет две записи в данных, но не доказывает два выбираемых сигнала. Механика сбора описана в [официальном материале Wube](https://www.factorio.com/blog/post/fff-385), runtime-поля — в [LuaAsteroidChunkPrototype](https://lua-api.factorio.com/latest/classes/LuaAsteroidChunkPrototype.html). Эти страницы поясняют модель; фактические значения видимости/alias для выбранной stable нужно получить отдельно.

Для каждого из четырёх астероидов:

1. Сохранить наблюдение пользователя: по одному варианту каждого куска. Повторное подтверждение числа вариантов не является незакрытым вопросом к пользователю.
2. Для единственного варианта получить фактические `type` и `name` из экспортированного blueprint или секции с учётом правил формата. Сохранить происхождение: это результат выбора из меню, не принудительная вставка сигнала. Если данных для сопоставления пока нет, отметить ровно этот технический пробел и продолжать независимую часть работы.
3. Исполнитель задачи дополнительно получает runtime-значения `hide_from_signal_gui` и `item_signal_alias`, если нужная среда доступна. Разбор этих полей не перекладывать на пользователя; отсутствующее поле сырого снимка не считать значением false или отсутствием alias в игре.

Эти пять случаев — локальные проверки спорных записей. Их разрешение само по себе не подтверждает полноту всего меню и не меняет `menuConfirmed` для полного профиля без отдельной сверки.

### Сигналы рецептов обработки астероидов

Пользователь дополнительно сообщает о наличии в меню сигналов дробления, переработки и продвинутого дробления. Учитывать их как отдельные сигналы рецептов, а не как вторые варианты самих кусков. Не исключать их при устранении пересечений item/asteroid-chunk и не объединять с предметным токеном.

В текущем сыром снимке Space Age 2.1.24 присутствуют следующие девять рецептов:

| Материал | Дробление — recipe/name | Переработка — recipe/name | Продвинутое дробление — recipe/name |
|---|---|---|---|
| Металлический | `recipe/metallic-asteroid-crushing` | `recipe/metallic-asteroid-reprocessing` | `recipe/advanced-metallic-asteroid-crushing` |
| Углеродный | `recipe/carbonic-asteroid-crushing` | `recipe/carbonic-asteroid-reprocessing` | `recipe/advanced-carbonic-asteroid-crushing` |
| Оксидный | `recipe/oxide-asteroid-crushing` | `recipe/oxide-asteroid-reprocessing` | `recipe/advanced-oxide-asteroid-crushing` |

Эта таблица перечисляет исходные ID снимка; наблюдение пользователя подтверждает наличие категорий операций, но не является отдельной выгрузкой каждого type/name. При следующей доработке проверить их включение в публичный набор по существующему правилу имён, связь с recipe-токенами и round-trip. Не вводить автоматически вложенность по аналогии с бочками: для них принято отдельное соглашение. Для прометиевого куска соответствующих рецептов с этими именами в текущем снимке нет; не генерировать их по аналогии и не приписывать пользователю утверждение об их наличии.

- [x] Регрессия: четыре сигнала кусков имеют по одному публичному пути; сырые пары не потеряны, игровые ключи явно сопоставлены.
- [x] Регрессия: сигналы рецептов обработки сохраняют отдельные ключи и не исчезают при разрешении коллизий кусков.

## Формат результата

Будущие производные файлы хранить отдельно от сырых снимков, например `data/signal-catalog/<version>/`: таблицы base/space-age, manifest и отчёты coverage/collisions/version-diff; человекочитаемое представление генерировать из того же JSON.

Строка содержит: gameVersion, profile, gameType, gameName, prototypeId, role, publicSection/publicName/publicPath либо явную причину отсутствия пути, group/subgroup и их order, prototype order, label.en/ru с labelSource/status, defaultQuality/правило явного качества, hidden/parameter/signal-selection status и его свидетельство, icon description/status, источники полей. stackSize/weight брать из настоящих данных, если включены; не вычислять rocket-capacity без отдельного подтверждённого правила.

Качество как тип сигнала и модификатор количества/канала различать. Не размножать каждую строку заранее на все качества; хранить таблицу качеств и разрешённость применения. Значения неизвестных полей маркировать, не подменять значениями по умолчанию.
