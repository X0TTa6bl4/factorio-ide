# Общая стратегия проверки

Эта стратегия применяется при будущей реализации задач эпика. Здесь нет отчёта об уже выполненных тестах.

## Окружение и уровни

Первая задача создаёт воспроизводимый Docker-контур. Устанавливаемые Node.js, пакетные инструменты, средства покрытия и браузерной автоматизации находятся в контейнерах. Выбранные версии образов и пакетов фиксируются. Исходники приложения остаются обычными ES-модулями; тестовые зависимости не становятся обязательной частью пользовательской страницы. Команды контура — [dev/README.md](../../../../dev/README.md). Результаты прогона задачи 0001 записаны в её `0000`.

- Unit: числовые функции, каналы, операции, условия, фильтры и локальные переходы.
- Contract: формы конфигурации, принадлежность сетей, ошибки, границы Worker и сериализации.
- Integration: трассы тиков, обратные связи, несколько источников, события, сообщения, расписания и сохранение.
- Browser: загрузка ES-модулей по HTTP, управление шагами и сценариями, диагностика, остановка зависшего кода, сохранение.
- Дифференциальные и генеративные: эталонный полный проход против оптимизированного; перестановка устройств; повтор с одинаковым seed; snapshot/restore.
- Игровые эталоны: версия, профиль данных, настройки, входы, ожидаемые выходы по тикам и происхождение результата.

## Максимальное покрытие ядра и комбинаторов

Для собственных модулей движка, числовой модели, сигналов, сетей и пяти типов комбинаторов целевой охват — 100% достижимых statements, lines, functions и branches. Отчёт формируется по каждому модулю, чтобы общий процент не скрывал пробелы. Включать неисполненные модули, ошибки и варианты конфигурации; не исключать файл ради повышения процента. Недостижимая ветвь требует обоснования и ревью; лучше устранить мёртвый код.

Этот критерий дополняется картой «правило → тест → ожидаемый результат → источник». Пройденные строки не доказывают правильность арифметики, метасигналов и порядка публикации. Для каждой поддержанной операции и комбинации режимов нужны обычные, граничные, пустые и ошибочные случаи. Для потенциально большого пространства комбинаций использовать классы эквивалентности, таблицы истинности, попарное и генеративное покрытие с фиксированным seed; не обещать исчерпывающий перебор всех значений int32.

Проверить чувствительность тестов к намеренным ошибкам в критических местах: знак/переполнение int32, порядок AND/OR, фильтр Each, чтение next вместо current, потеря вклада писателя, раннее сообщение и пропущенное пробуждение. Метод и инструмент выбрать в контейнерном контуре; не вводить отдельную производственную зависимость ради мутаций.

## Обязательные инварианты

- Пропущенный обычный канал читается как 0; нулевой итог отсутствует; совпадают только одинаковые ключи канала.
- Цвета выбирают источники; одинаковые каналы выбранных входов складываются по int32.
- Незаполненный операнд, пустая цветовая маска и отсутствующий сигнал — разные случаи.
- Все устройства читают одно опубликованное состояние тика. Новые выходы видны после общей границы.
- Вклад устройства хранится отдельно от суммы сети; изменение или исчезновение вклада не уничтожает вклад другого писателя.
- Цикл не приводит к рекурсивному исполнению; перестановка устройств не меняет результат.
- Reset и повтор с одинаковыми данными/seed дают одинаковую трассу.
- Ошибки валидации и исполнения имеют согласованную атомарность, а не случайные частичные изменения.
- История восстанавливает всё, что влияет на следующий тик, включая RNG, сценарии, сообщения и пробуждения.
- Ускорение сохраняет результат эталона, включая устройства, которые не просыпаются каждый тик.

## Статусы ожиданий и свидетельств

Матрицы задач — запланированные проверки. Игровую документацию, вручную рассчитанное ожидание и фактический запуск Factorio маркировать отдельно. Непроверенный игровой случай не выдавать за доказанное соответствие. При изменении stable или профиля повторить относящиеся к изменению эталоны; сохранять версию их происхождения.

Каждый регрессионный тест проверяет наблюдаемые сигналы/ошибки/трассу, а не копирует внутренний алгоритм. Случайные проверки сохраняют seed. Таймерные проверки опираются на управляемый тик, а не ожидание реального времени, кроме проверки прерывания Worker с обоснованным лимитом.

## Первый срез и происхождение ожиданий

Порядок подготовки: Docker-окружение 0001 → проверенная таблица Signal 0002 → токены/сети 0003 → движок 0004. Реализация движка начинается после приёмки таблицы. Положительные фикстуры используют реальные записи и публичные имена из неё; синтетические некорректные записи остаются инструментом негативных тестов.

Первый контур включает минимальные Constant/Arithmetic и EventCombinator с настоящим Worker. Начальное покрытие маркируется как проверка проектной модели. Для каждого арифметического ожидания отдельно указывать model / documentation / game-fixture, версию и источник. BigInt-оракул — проверка точности модели, а не эталон Factorio. Профиль base и малые тестовые наборы не отменяют полный формат сигнала и каталог; игровые данные не подменяются заглушками.
