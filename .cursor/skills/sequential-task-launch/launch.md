# Запуск очереди f logic

## 1. Проверка моделей и инструментов

До запуска или вопроса об очереди проверь фактическую модель чата по доступным сведениям среды. Допускается только Composer 2.5 (`composer-2.5`); не угадывай модель по стилю ответа и не выдавай себя за другую.

- Модель другая или не подтверждена → `say-wrong-model`, остановись.
- Нет запуска субагентов с точным `grok-4.7-high` → `say-unavailable`, остановись. Не используй другую модель или иной чат вместо субагента.
- При поддерживаемом Cursor API используй `Task`; при другом API — только эквивалентный запуск с подтверждённой поддержкой указанной модели. Наличие произвольного инструмента делегирования не подтверждает поддержку Grok.

## 2. Область и номера

Сначала установи область: самостоятельные задачи верхнего уровня либо дочерние задачи конкретного эпика. Используй явно указанный путь или однозначный контекст текущего поручения. Номера внутри эпика локальны: `0001` может означать и эпик, и его первую задачу.

Если область неоднозначна, задай `ask-scope`. Если область известна, но пользователь не выбрал задачи, задай `ask-tasks`. Используй доступный инструмент вопросов или обычный вопрос и дождись ответа.

- Явный список номеров → сохрани порядок пользователя; не добавляй другие задачи.
- «Все оставшиеся» / «все активные» → собери незавершённые задачи только выбранной области.
- Создание или адаптация скилла, описание эпика и обсуждение порядка не являются поручением запустить реализацию.

Не меняй номера и дерево задач. Не обходи соседние workspace.

## 3. Очередь и зависимости

Найди каталоги `NNNN-task-*` и `NNNN-bug-*` непосредственно в выбранной области. Эпик — контейнер: при поручении выполнить его задачи используй дочерние каталоги, не запускай эпик вместе с ними. Исключи `_archive/`, `_backlog/`, `media/`, шаги `0100`, `0200` и fix-up.

Корневой файл — единственный `0000-*.md`. При отсутствии или нескольких кандидатах сообщи проблему, не выбирай произвольно. Читай только метаданные, ссылки на корни задач и разделы порядка/зависимостей; исходники и подробный план реализации управляющему не нужны.

- `done` / `cancelled` → пропусти с указанием причины.
- `planned` / `in-progress` → кандидат на выполнение.
- `draft` / `blocked` → выясни по описанию, какой обязательный вход отсутствует; не запускай автоматически и не считай завершённой. Независимые готовые задачи допустимы в пределах порученной очереди; зависимые ждут.
- Статус отсутствует или неизвестен → уточни состояние, не считай задачу готовой к запуску.

Для «всех оставшихся» используй актуальный порядок зависимостей из корневого файла эпика, а не только сортировку номеров. В `0001-epic-_-f-logic-implementation/0000-f-logic-implementation.md` есть явная последовательность; в частности, `0010` и `0011` предшествуют общей приёмке `0005`. Не фиксируй копию всей последовательности в скилле. Без явного порядка выбери порядок по зависимостям, равноправные задачи — по номеру.

Для явного списка проверь предшественников перед каждым запуском. Если порядок пользователя противоречит зависимостям или нужной задачи нет в списке, сообщи конкретное препятствие и запроси решение; не расширяй и не переставляй список молча.

Пустая очередь → `say-none`. Неоднозначная область, цикл зависимостей или неразрешённый обязательный вход → остановка зависимой части с объяснением.

## 4. Один запуск

Управляющий чат только **запускает** субагента на номер задачи и передаёт handoff по § 4.1; не подменяет `work-orchestrator-ru` и не выбирает, как субагент делит работу внутри (в том числе свои вложенные `Task`).

Перед запуском в текущем контексте явно обозначь выбранный эпик/область и корневой файл задачи. Субагент должен наследовать этот контекст: голого номера без однозначной области недостаточно.

В Cursor вызови `Task` один раз. Сохраняй **Agent ID** из ответа — он нужен для `resume` и для handoff при обрыве.

```text
description: задача NNNN
prompt: начинай делать NNNN
model: grok-4.7-high
subagent_type: generalPurpose
run_in_background: false
```

Если пользователь поручил **продолжай** или запуск следует сразу после обрыва/abort субагента, `prompt` дополняй по § 4.1 (первая строка по-прежнему `начинай делать NNNN`).

Не делай второй вызов запуска до завершения первого. Для эквивалентного асинхронного API сохрани идентификатор субагента и дождись его ответа, сообщая пользователю существенный прогресс. Не создавай новый пользовательский чат.

### 4.1 Передача контекста (продолжай)

Управляющий чат **не реализует** задачу, но собирает служебную сводку для субагента, чтобы не терять прогресс между запусками.

**Когда применять:** поручение «продолжай», возобновление очереди после стопа/abort, новый субагент на тот же номер, переход к следующему номеру в той же сессии очереди.

**Источники (по приоритету):**

1. **Тот же номер NNNN, есть Agent ID** — `Task` с `resume` и коротко: продолжить с места остановки; при необходимости один абзац из последнего отчёта субагента в чате.
2. **Тот же номер, субагент оборван, ID нет** — транскрипт субагента в `agent-transcripts` (каталог `subagents/`): что прочитано, какие файлы затронуты, на каком шаге остановились, есть ли незакоммиченные правки (`git status` / краткий diff).
3. **Следующий номер по зависимостям** — итог **непосредственного предшественника** из его финального отчёта в чате (факты, тесты, ключевые пути в репозитории, ограничения «что осталось другим задачам»). Не дублируй весь эпик.
4. **Область** — эпик, корневой `0000-*.md` текущей задачи, статус `status:` (если не `done`, не врать о завершении).

**Формат `prompt`:**

```text
начинай делать NNNN

--- контекст передачи ---
Область: …
Предшественник / прошлый субагент: …
Сделано / проверено: …
Незавершённая работа: …
Репозиторий: …
```

Блок краткий и фактический; без копирования целых спецификаций и без подмены `work-orchestrator-ru` (субагент сам читает задачу).

**Resume vs новый субагент:** при обрыве той же задачи предпочитай `resume` с сохранённым Agent ID; новый субагент с handoff — только если `resume` недоступен или пользователь явно просит новый заход.

## 5. Ответ субагента

Если субагент задаёт вопрос пользователю, передай вопрос без изменения и дождись ответа. Не выбирай за пользователя и не переходи к следующему номеру. Ответ пользователя передай тому же субагенту без дополнений. Новые инструкции пользователя имеют приоритет над прежней очередью.

Возврат субагента сам по себе не означает готовность. Сопоставь его отчёт с `status:` корневого файла: `done` должен сопровождаться фактическими результатами обязательных проверок. Не запускай их повторно управляющим. Если отчёт и статус расходятся, запроси уточнение у того же субагента, не объявляя задачу готовой. Это служебное продолжение, а не новое задание `начинай делать NNNN`.

Ошибка, отказ запуска, недоступная обязательная проверка или блокер → сообщи фактическое состояние; не помечай задачу `done` и не запускай её зависимых. Не повторяй один и тот же неудачный запуск без изменившихся условий. Независимую часть можно продолжать, только если она входит в поручение и порядок пользователя это допускает.

## 6. Следующая задача и результат

После подтверждённого завершения перепроверь статус и зависимости следующей задачи: файлы могли измениться во время выполнения. Затем повтори одиночный запуск.

В конце дай по строке на задачу: завершена, пропущена, заблокирована или не запускалась, с краткой причиной для незавершённых. Реплику `{NNNN} готово` используй только для проверенно завершённой задачи. По требованию пользователя остановить очередь не запускай следующую и сообщи состояние текущего субагента.
